# odoshi-bench

The honest benchmark suite for the [shishi-odoshi](https://github.com/shishi-odoshi)
ecosystem: [odoshi](https://github.com/shishi-odoshi/odoshi) (the slim OTP-style
supervisor for Rails processes) measured against **foreman**, **overmind**,
**docker compose `restart: always`**, and an **unsupervised baseline** — on the
same template-generated Rails app, under the same load, with every contender
run the way its own docs recommend.

It exists to check odoshi's three claims with numbers, and to publish the
numbers either way:

1. **Fast recovery** — a SIGKILLed child is back and serving quickly (Track A).
2. **Near-zero beside-mode overhead** — supervised puma ≈ bare puma (Track B).
3. **Detection beyond PID-aliveness** — probes and heartbeats catch a child
   that is *alive but wedged*, which no PID-watcher can see (Track C).

## Honesty rules

These are the rules the harness is built around. If a number in this README
violates one of them, that is a bug — file an issue.

- **Medians of N ≥ 5 runs** in the full matrix, warmups discarded. (p95 of 5
  samples is the max — read it as "worst observed", not a distribution tail.)
- **Environment disclosed** with every run: hardware/CI class and the version
  of everything, embedded in `results/results.json` and the tables below.
- **Raw results committed per run, dated** — `results/raw/DATE-MODE.jsonl` is
  every individual measurement; the tables are generated from it
  (`scripts/render_results.rb`), never hand-edited.
- **No contender tuned worse than its docs recommend.** foreman runs plain
  `foreman start` (its docs delegate production supervision to `foreman
  export`); overmind gets `--auto-restart` (its documented supervision mode);
  compose gets `restart: always` plus a healthcheck; odoshi runs the exact
  `config/supervisor.rb` the template generates.
- **Every place a competitor beats odoshi is reported verbatim** — see
  [Findings](#findings).
- **Semantics tables explain *why* each contender behaves as it does.**
  foreman exiting the whole formation on child death is its documented
  design, so it is reported as `formation exited (documented)` — never
  scored as a crash. Non-detecting contenders in Track C get a factual
  "not detected within the window", because they have no detection
  mechanism, not because they malfunctioned.

## The tracks

**Track A — recovery under load.** One identical Rails app (generated from
[odoshi-template](https://github.com/shishi-odoshi/odoshi-template)'s
`template.rb`, Postgres, production env) under each contender, with 50 rps
against `/up` and one marker job enqueued per second. SIGKILL the puma
master: measure time-to-first-200 and count failed requests. In a separate
cycle, SIGKILL the Solid Queue supervisor: measure marker-row lag (kill →
first job *performed* after the kill). Every cycle is a fresh boot.

**Track B — overhead.** (1) Supervisor-process RSS + CPU over a steady
window under load — the supervisor process only, children excluded
(overmind's mandatory tmux server is reported alongside, added to nothing).
(2) Boot-to-`/up` per contender. (3) The key honesty test: `wrk` latency and
throughput against `/up`, odoshi beside-mode vs bare `puma`, identical
process complement (web + jobs) on both sides, warmup discarded. The
expected result is *no difference* — beside-mode puma is the same process
either way; a real difference is a qa-labeled finding on the odoshi repo,
not a number to bury.

**Track C — detection.** `POST /bench/wedge` flips a **process-local** flag
that makes `/up` answer 503 while the process stays alive (a restart cures
it — exactly a stuck threadpool or poisoned in-process state; the pattern is
odoshi's own `flaky_http_server` test fixture, in-app). Contenders: odoshi
with an HTTP probe + `degraded_restart_after`, odoshi with active heartbeats
self-reporting `degraded`, foreman, overmind, compose-with-healthcheck.
Measured: wedge trigger → first 200. Full-matrix observation window for
non-detectors: 120s.

**Track D — sidecar queue drain (stretch).** 1000 no-op jobs pre-enqueued on
one Postgres Solid Queue schema, drained by the Ruby worker (`bin/jobs`) vs
the [beam](https://github.com/shishi-odoshi/beam) Elixir worker, both from
their published artifacts.

## Running it

Requires Docker with Compose v2. The app image bakes a fresh
`rails new -m template.rb` app at build time plus the documented bench
patches (`app/patches/apply.sh`); all contenders run that one image.

```
scripts/bench.sh                       # full matrix (N=5, ~1.5–2h): the README numbers
scripts/bench.sh --mode ci             # reduced matrix (N=3, shorter windows): what CI runs
scripts/bench.sh --mode smoke          # N=1 plumbing check
scripts/bench.sh --tracks abcd         # include the stretch track D
scripts/bench.sh --tracks a --keep     # one track, leave the stack up
```

Outputs: `results/raw/DATE-MODE.jsonl` (every row), `results/results.json`
(aggregates + environment), README tables re-rendered in place.
`scripts/assert_sanity.rb` gates the run: odoshi must recover and detect
(regression check); competitors are never asserted to lose.

### CI

`.github/workflows/ci.yml` runs the **reduced matrix** (`--mode ci`,
tracks A/B/C, N=3, shorter observation windows — e.g. 60s instead of 120s
for Track C non-detectors) as a smoke/regression check on ubuntu runners,
uploading the results as an artifact. CI numbers are for regression
detection only; the README tables come from full local runs on disclosed
hardware. Track D is local-only.

## Methodology notes & caveats

- **Endpoint choice:** load and latency run against `/up` (no DB, minimal
  view work). That maximizes sensitivity to supervision overhead — a
  DB-bound endpoint would only shrink any difference.
- **Clocks:** every timestamp is taken inside the containers (one host
  kernel clock); the host only orchestrates. Kill instants are captured
  immediately *before* the `SIGKILL` (sub-ms apart) to avoid racing
  container teardown.
- **Recovery clock:** a dedicated 50ms-interval poller (`bench/wait_200.rb`),
  not the 50 rps load stream, decides time-to-first-200.
- **compose kills are real crashes:** processes run under `init: true`
  (tini), and the kill is a `pkill -9` *inside* the container, so the
  container exits and the restart policy applies. `docker kill` from
  outside would count as a manual stop, which docker deliberately does not
  restart.
- **foreman/overmind port assignment** uses their own `-p 3000` mechanism so
  web binds :3000 like every other contender.
- **odoshi numbers include its defaults:** the template config ships
  `backoff :exponential, base: 1` — roughly 1s of every odoshi recovery
  time is deliberate backoff, not detection latency. Reported as-is because
  that is what the template installs.
- **Track C windows:** detection contenders get the standard recovery
  timeout; non-detectors get the full 120s window (full mode) at N=2 —
  their non-detection is deterministic (no mechanism exists), so the window
  is a confirmation, not a distribution.
- **Track D caveats:** same job name, different runtimes — the Ruby side
  runs the full ActiveJob/Rails stack per execution, beam executes a
  registered Elixir handler; "drain" includes worker boot (Rails boot for
  `bin/jobs`, BEAM node start for the sidecar), "window" (first→last
  finish) excludes it; per-job *claim*-to-finish is not persisted by Solid
  Queue post-completion, so the reported distribution is finish-window
  based. Concurrency: Ruby worker `threads: 3, polling 0.1s` (queue.yml)
  vs beam defaults (`batch_size: 3`, 100ms polling) — the closest matching
  knobs that exist on both sides.
- **Bench surface deltas** to the generated app are exactly the contents of
  `app/patches/` (documented in `apply.sh`); every contender runs the same
  patched app.

## Repo layout

```
app/            Dockerfile (template-generated app + all contender tooling)
app/patches/    the documented deltas + Track C supervisor configs
bench/          in-container measurement tools (loadgen, pollers, samplers)
scripts/        host-side orchestration (bench.sh, per-track scripts, renderer)
beam/           Track D Elixir worker (consumes shishi-odoshi/beam from main)
results/        raw per-run JSONL (dated, committed) + aggregated results.json
```
